# 🌍 Travel Planner — Android Application

**TravelPlanner** — це мобільний додаток для Android, розроблений для зручного планування подорожей, управління бюджетом та організації списку локацій для відвідування. Проєкт пропонує реактивний інтерфейс для відстеження маршрутів та збереження пам'ятних місць.

---

## 🗂️ Моделі даних & CRUD

Логіка додатка базується на чотирьох ключових сунтостях зі зв'язками один-до-багатьох (*One-to-Many*):

1. **User (Користувач)**: Профіль мандрівника (ID, ім'я, email, статус авторизації).
2. **Trip (Подорож)**: Основна сутність, щр містить дані про подорож (назва, бюджет, дата, статус завершення, зв'язок з користувачем).
3. **Place (Місце)**: Конкретна локація всередині подорожі (назва, статус відвідування).
4. **PackingItem (Речі)**: Чекліст речей, які необхідно зібрати в дорогу (назва, категорія, прапорець «запаковано»).

### Реалізовані операції:
1. **Create**: Додавання подорожей, локацій та елементів багажу.
2. **Read (List/Object)**: Реактивне отримання списку подорожей та детальної інформації про них через `Flow`. Пошук користувачів за ID та Email.
3. **Update**: Оновлення статусу відвідування місць, маркування зібраних речей та зміна параметрів безпеки.
4. **Delete**: Каскадне видалення подорожі (автоматично очищає пов'язані місця та речі), а також захищене видалення профілю користувача.

## 🔐 Архітектура безпеки та захисту даних

У додатку реалізовано комплексний захист конфіденційної інформації користувача:

1. **Багатокористувацький біометричний вхід (Multi-user Flow):**
    * Біометричний сканер (`Touch ID / Face ID / Combined`) інтегровано на рівні заліза пристрою.
    * Реалізовано стратегію *«Останнього успішного користувача»*. Додаток запам'ятовує унікальний ID користувача, який останнім увімкнув захист. При перезапуску додатка кнопка біометрії автоматично підтягує саме його профіль. Інші користувачі пристрою можуть увійти за стандартною парольною формою.
2. **Автоматичне блокування у фоні (Session Timeout):**
    * За допомогою `AppLockController` додаток відстежує перехід у фоновий режим.
    * Користувач може налаштувати таймаут (15с, 30с, 1хв, 5хв). Якщо додаток згорнуто довше цього часу, поверх інтерфейсу відкривається захисний екран `AppLockScreen`, що вимагає повторну автентифікацію.
3. **Захист критичних дій (Critical Actions):**
    * Для виконання незворотних дій (таких як повне видалення профілю) створено екран-запобіжник `CriticalActionScreen`. Він вимагає обов'язкового сканування відбитка, унеможливлюючи випадкове або зловмисне видалення даних сторонніми особами.

## 🔄 Стратегія синхронізації: Offline-First

У додатку реалізовано стратегію **Offline-First**, оскільки доступ до планів подорожей має бути миттєвим навіть у літаку, горах чи в умовах роумінгу.

**Як це працює:**
*   **Читання:** Дані завжди завантажуються з локальної бази Room.
*   **Запис:** Будь-яка зміна спочатку зберігається локально зі статусом `SyncStatus.PENDING`.
*   **Синхронізація:** Додаток ініціює запит до API. При успішній відповіді запис отримує статус `SYNCED`. У разі помилки мережі статус стає `ERROR`, що дозволяє повторити спробу пізніше.

## 🌐 REST API Contract

Взаємодія з сервером побудована за принципом **REST API**. На даному етапі реалізовано сервісний шар `MockTripApiService`, який імітує мережеві запити з затримкою.

| Метод | Шлях | Body / Params                                 | Що повертає | Опис |
| :--- | :--- |:----------------------------------------------| :--- | :--- |
| **GET** | `/trips` | —                                             | `List<TripDto>` | Отримати список усіх подорожей користувача |
| **GET** | `/trips/{id}` | **Path** `id`                                 | `TripDto` | Отримати деталі однієї подорожі |
| **POST** | `/trips` | **Body:** `title`, `budget`, `date`, `userId` | `TripDto` (Created) | Створити нову подорож |
| **DELETE** | `/trips/{id}` | **Path** `id`                          | `204 No Content` | Видалити подорож та всі її локації |
| **POST** | `/trips/{id}/places` | **Path:** `id`, **Body:** `name`, `isVisited` | `PlaceDto` | Додати локацію до подорожі |
| **GET** | `/profile` | —                                             | `UserDto` | Отримати дані поточного профілю |

## Автоматизоване тестування (Unit Tests)

Якість коду, стабільність бізнес-логіки, обробка потоків `StateFlow` та збереження конфіденційних даних підтверджені системою локальних Unit-тестів. Тестування побудоване на базі фреймворку **MockK** з використанням `kotlinx-coroutines-test` для імітації асинхронних операцій без запуску емулятора.

### Покриття тестових модулів:

1. **🔐 Біометрія та Безпека (`BiometricAndStorageTest`, `SecurityViewModelTest`)**
   * **Апаратні сценарії:** Імітація поведінки пристрою без датчика безпеки (`SensorType.UNSUPPORTED`), а також перевірка повернення станів успішного сканування (`Success`) та скасування операції користувачем (`Failed`).
   * **Збереження конфігурації:** Перевірка зчитування та запису таймаутів автоблокування системи та прапорців активації захисту без спотворення типів даних.
   * **Життєвий цикл UI:** Валідація миттєвого переходу станів `SecurityViewModel` у положення `Authenticating` та `Success`. Перевірка автоматичного очищення сесії та ID користувача при вимкненні захисту.

2. **🔑 Авторизація та Сесії (`AuthViewModelTest`)**
   * Перевірка успішного входу (`AuthState.Success`) за коректних облікових даних.
   * Обробка помилок авторизації (`AuthState.Error`) з валідацією локалізованих повідомлень про невірний пароль.
   * Тестування сценаріїв реєстрації нового користувача, обробки ексепшенів сервера (наприклад, дублікат Email) та скидання стану сесії до `Idle` при виході.

3. **🎒 Збір речей & Мапери (`PackingMapperTest`, `TripViewModelPackingTest`)**
   * **Обчислювальні алгоритми:** Тестування чистих функцій мапера для підрахунку відсотка прогресу збору багажу (наприклад, 2 з 4 речей = 50%), фільтрації запакованого та правильного групування за категоріями (`DOCUMENTS`, `CLOTHING`).
   * **Інтеграція з БД:** Перевірка викликів реактивного оновлення Room при додаванні, видаленні, перемиканні прапорця та редагуванні назви речі.

4. **📡 Сповіщення та Веб-сокети (`TripViewModelNotificationsTest`)**
   * Тестування логіки очищення списку повідомлень та маркування всіх сповіщень як прочитаних.
   * Перевірка захисного механізму підключення до сокету (`startWebSocket` виконує коннект тільки якщо поточний стан системи — `Disconnected`).

5. **🗺 Керування подорожами (`TripViewModelTripsTest`)**
   * Перевірка бізнес-правил безпеки: блокування методів `addTrip()` та `deleteTrip()` (з `exactly = 0` викликами репозиторію), якщо у системі немає активного авторизованого користувача (`user == null`).
   * Валідація початкового стану сортування списку турів.
